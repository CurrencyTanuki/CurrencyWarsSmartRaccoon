# 0.2.791 更新说明（2026-08-03 下午）

## 修复：节点反复识别错误（"节点 1-8/1-0 战斗开始"反复刷屏）

### 现象（用户实测 0.2.790）
- 日志反复出现"节点 1-8 战斗开始"与"节点 1-0 战斗开始"交替，间隔最短 4 秒；
- 游戏顶部实际显示"1-1 66%"，但程序把 1-1 识别成 1-8/1-0；
- 备战页 1-1 也一度显示"进入备战节点 未知节点"。

### 根因（三层叠加）
1. **OCR 误读**：战斗页节点号完全依赖 OCR（页面 ID 无节点信息），
   `NodePattern` 正则允许 node=0~9，本地化数字识别 stage 也允许 0~9——
   OCR 把 1-1 读成 1-0 或 1-8 时被当作合法节点号接受。
2. **消息文案错位**：节点未知的战斗帧（如过场被误判为战斗页）按 Unknown
   处理，但"战斗开始"消息用的是原始 frame.PageFamily（Battle）——
   Unknown 确认也被输出成"节点 X 战斗开始"。
3. **去抖盲区**：战斗开始去抖（10 秒）只拦 Battle 确认，不拦 Unknown 确认；
   Battle↔Unknown 反复切换时每次 Unknown 确认都触发一次假"战斗开始"。
   （用户故意失焦 92 秒期间帧抖动放大触发，属测试行为非故障。）

### 修复（保守，未动识别逻辑与输出）
1. `NodePattern` 正则 node 范围 `[0-9]` → `[1-9]`：拒绝 1-0 这类非法节点号；
2. `ReadLocalizedNodeDigits` 的 stage 识别范围 0~9 → 1~9（同源修复）；
3. `Phase2OperationalStateTracker.PageTransitionMessage` 改用 `effectivePage`
   而非原始 `frame.PageFamily`：节点未知的战斗帧不再输出假的"战斗开始"，
   而是明确"画面处于过场或无法可靠识别；页面已安全跳过"。
4. 曾尝试"战斗节点连续 2 帧一致才采信"，回退——它会破坏合法的
   1-1→1-2 节点推进契约（多个既有测试失败），最终未采用。

### 说明
- 1-8 本身是合法节点号（1~9），OCR 把 1-1 读成 1-8 无法从正则层杜绝；
  但修复后节点未知帧不再误报战斗开始，且 1-0 被拒绝，反复刷屏会消失。
- 真正"战斗开始"仍正常输出（已知节点 + 页面确认），不影响节点历史记录。
