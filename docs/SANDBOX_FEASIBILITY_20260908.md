# 帧沙箱(Frame Sandbox)可行性案 —— 2026-09-08 值守班

> 用户动机:五费聘用书试炼从未在实机刷出过,永远等不到真帧;需要在不依赖游戏真实产出的前提下,
> 验证软件能否跑通"我们认为的最优路径"(含五费聘用书试炼段、三星五费终局段)。
> 思路(用户原话):给程序喂已有图片让它误以为在跟真实游戏交互,沿最优路径放帧、看它的反应与输出;
> 输出出现不符合预期的操作=软件有问题。

---

## 一、结论:可行,且接缝现成

软件是严格分层的:识别/决策/操作层全部只依赖 4 个基础设施接口,一个真实游戏窗口都不是硬依赖。
沙箱 = **DI 层换掉 4 个实现,决策/操作/识别代码零改动**。

| 接口 | 现实现 | 沙箱实现 | 依据 |
|---|---|---|---|
| `IGameCapture` | WindowsGraphicsGameCapture(WGC 抓真窗口) | **FileSequenceGameCapture**:按脚本逐帧返回 PNG 解码的 CaptureFrame | 单方法接口 `CaptureAsync(GameWindowInfo,ct)→CaptureFrame`(CaptureFrame.cs:93);CaptureFrame=BGRA 像素+时间戳,PNG 解码即可构造 |
| `IInputController` | Win32InputController(真实鼠标/键盘) | **RecordingInputController**:全部操作记入 sandbox-ops.jsonl,返回 Success(可按脚本模拟失败) | 4 方法接口(InputModels.cs:66):Click/Drag/PressKey/ClickWithModifier,返回 ActionResult |
| `IGameWindowService` | 枚举真实窗口 | **StubWindowService**:返回假 GameWindowInfo(handle=任意非 0,ClientArea=1920×1080) | GameWindowInfo 是纯 record(GameWindowInfo.cs:29),可直接构造;FindCandidates/IsForeground/BringToForeground 全部假答 |
| `IGameForegroundGuard` | 真实前台检测 | **AlwaysForegroundGuard**:恒真 | 前台守卫(rule 二.2)在沙箱里必须放行 |

模式入口:`--frame-sandbox <脚本.json>` 启动参数,与 `--command-test` 同型的 App.OnStartup 分支;
CommandTestWindow 保留(STATUS 可查状态),DECIDE 照常驱动决策层,只是"游戏"换成了帧序列。

## 二、脚本=驱动器+裁判(核心设计)

每个脚本步 = 一帧图 + 这一步允许的操作集:

```json
{ "steps": [
  { "image": "frames/01_home.png",
    "expect": [ { "op": "click", "near": [960, 540], "tol": 30, "note": "主界面进玩法" } ] },
  { "image": "frames/02_wish_trial_5cost.png",
    "expect": [ { "op": "click", "near": [x, y], "tol": 30, "note": "M3 选五费聘用书" } ] }
]}
```

- **推进规则**:当前帧持续供应给每次捕获(引擎等待期重复捕获同一帧=自然通过等待);
  当前步的 expect 全部被满足(操作类型+坐标±tol 命中)→ 切下一帧。
- **裁判规则**:出现 expect 之外的操作=违规,记入 sandbox-violations;当前步超时(默认 120s)未满足
  =违规(软件没做/做错);脚本走完=PASS。
- **这正好实现用户口径**:软件总有一条我们认为的最优路径→只生成该路径的图集;任何偏离=软件问题。
- 操作层坐标是写死的标准几何(rule 三.1),无随机抖动,tol=30px 足够。

## 四、能验证什么/不能验证什么(边界声明)

- ✅ 能验:决策层分支(状态机在给定画面序列下发出的操作序列)、操作层坐标几何、页面判定→分流、
  弹框应答优先级(M3/盛会)、弃局链分流、四.13a/四.5 等拍板规则的代码实现、失败注入下的恢复链
  (RecordingInputController 可按脚本让第 N 次操作失败,专测重试/换路线口径)。
- ❌ 不能验:识别层对"从未见过画面"的认读(没真帧就没真模板匹配)、真实动画时序(帧是静态的,
  等待类守卫会被静态帧"轻松通过"——测试偏松方向,不会误报好)、真机输入生效率(拖拽 hold 等)。
- **定性**:沙箱 PASS=软件在预期画面序列下走预期路径;≠实机必过(识别漂移/动画竞态仍在)。

## 五、已知技术风险与对策

1. **切帧时机 vs 操作后自证**:引擎"操作后重扫自证"(如 A4 拖后重扫面板)在切帧后恰好读到"已生效"
   画面=符合真实时序;真正要防的是 player 切帧过早让"动画等待"全部秒过。对策:expect 支持可选
   `minDelay`(v2),v1 先接受测试偏松。
2. **录屏**:DECIDE 的 GrailRollingRecorder 共用 IGameCapture,沙箱里它会录静态帧(无害),或
   ffmpeg 缺失自动跳过;沙箱产物统一隔离到 runs/sandbox-* 目录,不污染实局历史(用户令:弃局不入
   历史的隔离精神同样适用)。
3. **时钟**:CaptureFrame.CapturedAt=服务时刻(现在),帧龄看门狗自然通过。
4. **性能**:每帧 3.3MB PNG 解码,捕获频率低,无压力。

## 六、方案四点检查单(铁律 8)

1. **不违背既有设计**:只替换 4 个基础设施接口实现;决策/操作/识别管线零改动;与"统一识别流"
   (单捕获器+单识别器分发)架构一致——沙箱换的正是那个捕获器。
2. **不改用户已拍板内容**:零规则口径触碰;新增启动参数属测试台既有模式扩展(--command-test 同族)。
3. **不违背游戏机制**:帧全部来自真实游戏截图;序列=用户认可的最优路径。
4. **不违背指令集/决策树**:不新增指令、不改树;只是把"游戏"换成"录好的游戏"。
