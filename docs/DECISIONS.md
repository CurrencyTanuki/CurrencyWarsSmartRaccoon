# 关键决策记录

> 本文件记录当前有效决策。旧文档若与“已接受”决策冲突，以本文件为准；“建议”或“待确认”不等于已经修改代码。

## D-001 功能完成采用四级证据

- 状态：已接受
- 日期：2026-07-26
- 决策：区分编译通过、自动测试通过、离线视觉回放通过、当前版本游戏实机跑通。
- 原因：单元测试、Fake 状态机和函数存在不能证明游戏中可用。
- 后果：`PROJECT_STATUS.md` 的每项能力必须注明最高证据等级；新产物不能继承旧产物的实机结论。

## D-002 当前生产主路径只有一条

- 状态：已接受
- 日期：2026-07-26
- 决策：以 `App.xaml.cs` 实际 DI 装配的 `MainViewModel → OpeningRerollLoopCoordinator → CurrencyWarsNavigationTask` 为生产路径。
- 原因：仓库中仍存在 `OpeningRerollTask`、`TemplateOpeningReader`、`OpeningRuleEvaluator` 等旧平行实现。
- 后果：旧路径和 `config/recognition.json`、`config/opening-rules.json` 不得被当作当前运行时能力；后续应迁移或标记 legacy，不能继续双轨扩展。

## D-003 自动刷取不设总轮数或总时间上限

- 状态：已接受
- 日期：2026-07-26
- 决策：自动模式持续运行，直到满足条件、用户停止或发生必须安全停止的危险状态；观察单轮可以有局部超时。
- 原因：长期挂机目标不应被任意总轮数/总时长截断。
- 后果：每个动作仍必须有有限尝试预算。预算耗尽后重新识别、切换恢复路线或安全停止，禁止无限固定坐标点击。

## D-004 失焦暂停，回焦恢复

- 状态：已接受
- 日期：2026-07-26
- 决策：自动任务执行期间游戏失去前台焦点时暂停；确认回焦并稳定后从当前步骤恢复。
- 原因：避免切出游戏后误点桌面，也符合长时间挂机使用方式。
- 后果：所有捕获/输入任务必须通过 `IGameForegroundGuard`；暂停时间不计入活动超时。当前只有单元测试，仍需实机验收。

## D-005 未知页面默认 Esc 恢复

- 状态：已接受
- 日期：2026-07-26
- 决策：未知页面不点击，先执行受控 Esc，重新截图并分类；恢复后重新进入状态机。
- 原因：Esc 是多数非危险覆盖层的通用返回动作。
- 后果：Esc 也必须有限次、可取消并记录；若进入危险确认页或连续无法恢复，安全停止。

## D-006 检测到已有对局必须停止

- 状态：已接受
- 日期：2026-07-26
- 决策：识别 `rank_difficulty_in_progress` 后返回 `ActiveRunDetected`，不继续任何自动操作。
- 原因：用户现有进度优先级高于自动任务。
- 后果：该页面的模板、优先级和回归测试属于安全关键资产，变更需要当前版本实机复验。

## D-007 图像识别采用多帧、多方法和恢复路线

- 状态：已接受
- 日期：2026-07-26
- 决策：重要识别使用多帧稳定、模板/OCR/布局交叉确认、重试和备用恢复，思想参考 BetterGI，但不复制其代码或资源。
- 原因：一次识别失败不应中断挂机，一次误识别也不应触发危险输入。
- 后果：当前多数页面只有单锚点，是待偿还技术债；危险页面优先增加第二锚点或独立确认方法。

## D-008 上游 JSON 先进入原始层，再转换为运行时数据

- 状态：已接受
- 日期：2026-07-26
- 决策：数据与攻略知识库输出只视为 raw 输入；先 schema 校验，再转换和生成报告，最后由运行时加载规范化 JSON。
- 原因：上游字段、ID、版本和枚举可能与当前 C# 模型不一致。
- 后果：不得删除上游未知字段，不得手工复制，不得覆盖正在由上游对话写入的同名文件。当前流水线尚未完成，`data/4.4` 暂时保持只读生产输入。

## D-009 UI 采用完整深蓝主题

- 状态：已接受
- 日期：2026-07-26
- 决策：所有主窗口、设置、弹窗和悬浮控件使用统一深蓝现代主题，不接受未经设计的默认白色控件。
- 原因：这是产品体验边界，也有利于区分安全状态、警告和故障。
- 后果：新增控件必须复用或扩展主题资源；视觉验收属于交付的一部分。

## D-010 不重写已有实机证据的正向流程

- 状态：已接受
- 日期：2026-07-26
- 决策：在没有明确缺陷和回归方案时，不重写 HUD → 1-1 正向导航；优先局部修复、增加测试和证据。
- 原因：旧产物已有一次完整正向实机日志，整体重写会丢失已知行为。
- 后果：涉及页面 ID、动作坐标、模板阈值和导航顺序的变更必须说明影响并做回归。

## D-011 构建目录名称不代表可发布

## D-012 未实机验证的奖励关默认关闭

- 状态：待确认并实施

- 影响：不删除功能；用户显式开启时仍可测试。需要一次小范围代码/UI 修改和回归，未在本次审计中擅自执行。

## D-014 投资环境只支持正选

- 状态：已确认
- 日期：2026-07-26
- 决策：投资环境只表达“希望出现其中之一”，不提供排除语义。
- 需求证据：本次总控交接要求。
- 代码证据：`MainViewModel` 构造投资环境选择项时不允许 forbidden；`OpeningFilterEvaluatorTests.InvestmentPreferencesAreOrWhileEnemyRequirementsRemainAnd` 覆盖正选“或”语义。
- 影响：UI、schema 和上游转换不得为投资环境擅自引入负选；若产品规则改变，必须新增决策记录和迁移方案。

## D-015 敌人阵营与负面词条支持正选和排除

- 状态：已确认
- 日期：2026-07-26
- 决策：敌人阵营、敌人负面词条均可配置为 `Require` 或 `Reject`；正选条件必须满足，排除条件命中即拒绝。
- 代码证据：`src/CurrencyWarsAssistant.Game/OpeningFilters.cs` 的 `OpeningFilterMode.Require/Reject` 和筛选模型；相关测试位于 `OpeningFilterEvaluatorTests`。
- 影响：数据枚举、UI 选择态、序列化和转换层必须保留 Require/Reject 的区别。

## D-016 特殊组合必须全部条件同时出现才触发

- 状态：已确认
- 日期：2026-07-26
- 决策：特殊排除组合内部采用“且”；只有组合中的全部条件在同一开局同时出现时才判定命中，部分出现不得误杀。
- 代码证据：`OpeningFilterEvaluatorTests.RejectedCombinationOnlyViolatesWhenFullyHit`。
- 影响：不得把特殊组合扁平化为若干独立排除项；schema 必须保存组合边界。

## D-017 多套刷取方案之间采用“或”

- 状态：已确认
- 日期：2026-07-26
- 决策：每套方案内部按自己的分类规则完整判断；多套方案之间为 OR，任意完整方案满足即可保留。
- 代码证据：`OpeningFilterEvaluatorTests.MultipleProfilesAreOrAlternatives`、`ProfilesUseAndAcrossCategoriesAndOrWithinPositiveChoices`。
- 影响：不得把不同方案预先合并成一个筛选集合，否则会产生原本不存在的混合命中。

## D-018 同时命中多套方案时随机锁定一套完整方案

- 状态：已确认
- 日期：2026-07-26
- 决策：若同一开局命中多套方案，协调器随机选择其中一套并在后续流程中保持该方案整体；不得混合不同方案的投资环境、投资策略、角色或排除条件。
- 代码证据：`OpeningRerollLoopCoordinatorTests.MultipleMatchedProfilesLockOneCompleteProfileAtRandom`；协调器保存 selected profile 并据此构造奖励关选项。
- 影响：日志必须记录候选方案和最终锁定方案；后续阶段只能接收锁定方案 ID/快照。

## D-020 旧计划中的总轮数/总时长限制不再是现行规则

- 状态：已确认
- 日期：2026-07-26
- 决策：自动刷取没有总轮数和总时间上限；旧文档中的最大轮数/最大时长属于历史方案。单次危险动作仍必须有有限尝试、恢复和安全停止预算。
- 代码证据：`OpeningRerollLoopOptions` 使用可空总上限，`MainViewModel` 自动模式传入空值；测试 `DefaultAutomaticRunHasNoOverallLimits`、`DefaultAutomaticRunContinuesBeyondFormerRoundLimit`。
- 影响：不得重新加入静默总时限；也不得把“无总上限”误解为允许无限重复固定输入。

## D-021 每次 Bug 修复生成递增候选包

- 状态：已确认
- 日期：2026-07-26
- 决策：每次完成一个 Bug 修复并通过完整测试后，生成新的 `artifacts/live-test-N` 候选应用包供用户实机测试；编号递增，禁止覆盖旧候选。
- 需求证据：用户明确要求每次修复后都提供新应用程序包，本轮角色卡修复对应 `live-test-31`。
- 影响：候选包必须包含构建 manifest、测试结果、核心二进制 hash、包含的修复和未修问题；生成候选包不等于 L4，只有绑定该包的实机日志和结果才能提升证据等级。

## D-022 布阵后备战席出售采用三档显式策略

- 状态：已确认
- 日期：2026-07-26
- 决策：完成 1-1 单次布阵并逐角色验证后，备战席出售可配置为“出售全部可卖角色”“仅当全部可卖价值能使当前金币达到 10/20 利息阈值时出售”“完全不卖”；默认完全不卖。
- 保留边界：已上场角色、用户显式勾选保留的角色永不进入出售候选；开启“三仙舟 + 2持续伤害”自动规则时，符合既有低费羁绊谓词的角色也自动保留。利息模式金币无法连续稳定识别时必须不卖。
- 安全边界：只在稳定 `preparation_1_1` 页面执行，失焦暂停，未知页最多一次 Esc 恢复；每名角色有限拖动并以连续空槽帧验证，失败停止后续出售和奖励关。
- 影响：该策略属于 B 段实验能力，不改变 `OpeningFilterEvaluator` 或锁定开局方案语义，也不代表后期全局经济/人口识别已实现；需 `live-test-34` 实机证据后才能提升为 L4。

## D-023 全局采用最小 Token 验证策略

- 状态：已确认，覆盖 D-021 中“每次必须完整测试”的执行要求
- 日期：2026-07-27
- 决策：所有任务采用最小读取、最小修改、一次定向测试和一次必要构建；不重复全量测试、构建、哈希、审计或多代理交叉验证。
- 安全边界：危险输入和正式候选仍必须保留最小安全门禁；未运行的验证必须明确写“未运行”，不得把定向测试冒充全量或实机通过。

## D-024 自动运行异常进入持续监测，不终止任务

- 状态：已确认，下一轮统一实施
- 日期：2026-07-27
- 决策：自动运行只能由软件操作面板或取消令牌主动停止。恢复手段耗尽后进入无输入的持续页面监测；识别到主界面、货币战争主页或与当前进度一致的已知安全页后，自动重新接入状态机继续。
- 危险边界：已有进行中对局、页面无法证明可安全输入或可能触发撤退/放弃结算时，停止危险输入但不终止程序，保持被动监测；不得盲点未知坐标。
- 影响：下一轮统一改造 Coordinator、导航、开局恢复、奖励关和结算返回值。`live-test-68` 只修已授权结算链的持续推进，不声称完成全局改造。
