## 5. Highest-priority unfinished bugs

### 5.1 Node gold semantics are wrong

Relevant file:

`src\CurrencyWarsAssistant.Tasks\HistoricalDashboardProjection.cs`

Current behavior:

- `ObservePreparation` stores `snapshot.Economy` as `PreBattleGold` on the
  current node.
- `RebuildSnapshot` exposes `PreBattleGold` as `AbsoluteGold`.
- Therefore the `1-2` row keeps the gold seen before the `1-2` battle (`0`),
  even after the next preparation page shows the post-node balance (`20`).

Required behavior:

- Keep pre-battle gold internally if other reports need it.
- Add/derive a post-node or ending-gold value.
- When a reliable next preparation node is confirmed, use its first reliable
  gold balance to backfill the immediately preceding finalized node.
- The history dashboard should display the post-node balance.
- Never use `0`, empty text, or a guessed value when the field is unknown.
- Preserve raw evidence and do not globally lower OCR thresholds.

The supplied screenshot should be used to verify that visible gold `20` is
recognized. If OCR already returns `20`, fix only the projection/timing. If it
does not, inspect `Phase2RecognitionRegions.EconomyValue` and its preprocessing
without reintroducing the old `3 -> 73` regression.

### 5.3 Genuine settlement reward is being discarded

Relevant file and exact root cause:

`src\CurrencyWarsAssistant.Tasks\Phase2OperationalStateTracker.cs`

Current finalization contains:

```csharp
int? goldReward = !isRewardNode &&
                  settlement?.SettlementGoldReward.Status ==
                  ObservationStatus.Known
    ? settlement.SettlementGoldReward.Value
    : null;
```

This was introduced to reject a bogus `841` that came from a reward-node
settlement crop containing unrelated UI. It is now too broad: the real `1-2`
challenge-success analysis has a semantically valid recognized reward `6`, but
the final node record discards it solely because `isRewardNode` is true.

Relevant regression test currently encoding the overbroad behavior:

`tests\CurrencyWarsAssistant.Tests\Phase2BattleOutcomeHealthTests.cs`

`RewardBattle_IsPerfectAndIgnoresNonexistentSettlementGoldRow` creates a fake
known value `841` without semantic evidence and expects null.

Required fix:

- Do not accept arbitrary OCR from a region that does not contain the
  settlement reward row.
- Do accept a bounded, semantically anchored `SettlementGoldReward` from a
  real `challenge_success` page, including reward nodes.
- Distinguish "valid settlement reward evidence" from "number happened to be in
  the crop"; do not simply remove the reward-node guard.
- Add regression coverage for both rejected `841` and accepted real reward
  `6`.
- A conservative fallback may derive an unresolved gain only from reliable
  pre/post gold observations, but it must be labelled derived and must not
  fabricate a settlement reward.

### 5.4 Very short yellow challenge-success page

Relevant file:

`src\CurrencyWarsAssistant.Tasks\Phase2RealtimeRecognitionPipeline.cs`

Current facts:

- capture interval is 200 ms (5 FPS);
- `challenge_success` is in `FastPageIds`;
- page boundaries enqueue the current frame plus retained predecessors into a
  bounded critical queue;
- critical queue capacity is 12.

The user reports that the yellow page can flash even faster in normal play.
Do not add more OCR to every frame. Prefer a small, bounded capture burst near
battle-end/page-boundary conditions, or otherwise ensure the first fast
`challenge_success` match is locked immediately. Critical frames must never be
coalesced away by ordinary frames. Verify with a replay sequence in which the
yellow page lasts only one captured frame.

### 5.5 Safe new-run detection after a rejected mid-run attempt

New user rule:

- a player may abandon after several nodes and reroll, returning to `1-1`;
- the old run must be archived/closed or kept separately, never overwritten;
- one or a few frames claiming `1-1` are not sufficient because OCR may be
  wrong;
- first mark the regression as a pending suspected new run;
- only after a reliably finalized new `1-1` battle proves the reset may the
  previous run be sealed and a new run created.

Implement this in the shared run lifecycle/checkpoint path, not in the overlay.
Likely touch points:

- `src\CurrencyWarsAssistant.Tasks\Phase2LiveCollectionService.cs`
- `src\CurrencyWarsAssistant.Tasks\Phase2OperationalStateTracker.cs`
- `src\CurrencyWarsAssistant.Tasks\RunCheckpoint*.cs`
- existing resume policy in
  `src\CurrencyWarsAssistant.App\SituationAnalysisViewModel.cs`

Requirements:

- node regression creates pending evidence only;
- keep writing the existing run safely until confirmation;
- confirmation requires a finalized `1-1` battle plus consistent preparation /
  battle / settlement transition evidence;
- seal the prior run as abandoned/incomplete (do not delete by default);
- create a distinct run ID and continue recording;
- reset per-run identity caches only after the boundary is committed;
- make the operation idempotent;
- a false `1-1` OCR observation must leave the old run untouched.
