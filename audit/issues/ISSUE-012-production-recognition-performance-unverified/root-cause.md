# ISSUE-012 根因与最小修改

## 结论

正式识别没有稳定、持续超过 2 秒的证据，不应修改生产识别器、并发、阈值或预热逻辑。全量红灯的根因是历史 `RecognitionPerformanceTests` 使用非生产 Windows OCR 构造，却被当作正式 App 性能门。

同一张 SHA-256 为 `5ABD13EB...FE96` 的 2560×1440 图片：

- 旧测试隔离结果：6.03 / 11.95 / 5.16 秒；
- 正式 DI 非连续批测：1.858 / 1.603 / 1.507 / 1.456 / 1.435 秒；
- 正式 DI 连续序列：1.913 / 1.694 / 1.503 / 1.439 / 1.449 秒（批测总耗时）；对应 analyzer 为 1.846 / 1.644 / 1.452 / 1.389 / 1.399 秒。

差异来自 OCR provider、并发、fallback、页面分类和完整 App 配置不同，而不是同一生产路径在测试中变慢。

## 正式性能边界

37 次有效测量、12 个唯一图片哈希的 `perf:situation total`：

- min 526.1 ms；median 1389.1 ms；mean 1281.0 ms；p95 1869.1 ms；max 2062.3 ms；
- 36/37 低于 2 秒；唯一超过 2 秒的是原生 1080P 连续序列的首帧 2062.3 ms；后五帧为 1286.8、1331.2、1460.8、1170.2、1156.9 ms；
- 9 张战斗页全部 526.1–891.7 ms；
- 备战页稳态可降至 1156.9–1460.8 ms，但冷首 1–2 帧可能超过 1.5 秒。

1.5 秒是变化帧节律和 `DropStaleFrames` 触发阈值，不是每一帧必须满足的硬断言。识别超过该值时，当前帧仍先完成并输出，然后清理陈旧队列；ISSUE-010 已修复最新关键帧被误删。2 秒是普通帧节律，本轮没有持续超过 2 秒的序列。

唯一一次 2062.3 ms 冷首帧说明仍有性能余量，不能宣称所有帧绝对低于 2 秒。阶段延迟分散在 progress、formation、named 和首次 OCR 路径，没有收敛为单一可安全修改的热点。贸然调整并发、阈值或业务识别会扩大正确性回归风险，因此本项不改生产代码。

批测不包含桌面捕获、实时帧选择、队列、状态合并、持久化和界面刷新。最终实时链仍需实机验收；冷首帧性能余量保留为已知边界，不冒充已优化。

## 最小修改

只把旧测试从全量自动门禁改为静态 Skip：

```diff
-    [Fact]
+    [Fact(Skip = "Legacy non-production Windows OCR benchmark; validate production performance separately with App --phase2-batch-test evidence.")]
```

测试主体、旧断言和生产代码均未改。静态 Skip 不能通过 `--filter` 重新启用，因此不把该 C# 方法描述为“显式可运行”；真正的手工性能入口是正式 App `--phase2-batch-test`。
