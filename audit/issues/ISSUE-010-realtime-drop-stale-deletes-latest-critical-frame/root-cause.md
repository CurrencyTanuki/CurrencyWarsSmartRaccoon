# ISSUE-010 根因与修复边界

## 根因

`DropStaleFrames()` 先找到 `lastCritical`，但在 `items.Count > 2` 且最新关键帧后面还有队尾普通帧的缺陷分支中，循环命中该关键帧时只把 `keepCritical` 设为 `false`，随后仍执行无条件 `items.RemoveFirst()`。注释所说的“保留该关键帧”没有对应控制流，因此该分支会删除应保留的最新关键帧。若最新关键帧本身就是队尾，循环会在它之前停止，不属于本次缺陷分支。

这是确定性的队列清理逻辑错误，不是 OCR、识别器、状态合并或线程竞态。

## 最小修复边界

只修改：

- `src/CurrencyWarsAssistant.Tasks/Phase2RealtimeRecognitionPipeline.cs` 中 `Phase2BoundedRecognitionQueue.DropStaleFrames()`。

目标行为：

- 有关键帧且最后一帧为普通帧时，只保留最新关键帧与最后一帧，并保持原顺序；
- 在 `items.Count > 2` 的清理分支中，最后一帧本身为关键帧时清理到最后一帧；
- `items.Count <= 2` 时维持既有早退语义，不额外删除两项以内的关键证据；
- 若清理分支中没有关键帧，则清理到最后一帧；
- 每删除一项都同步消费一个 `SemaphoreSlim` 可用计数，避免空队列被错误唤醒或有效项无信号。

不修改：

- 队列容量或关键帧容量；
- `Enqueue`、`DequeueAsync`、帧选择器、1.5 秒阈值；
- OCR、页面分类、tracker、存储或历史界面；
- 当前 7 个既有失败对应的其他问题。

最终实现删除了无效的 `keepCritical` 状态。当队头到达 `lastCritical` 时直接停止清理；在此之前每删除一个旧项，仍按原逻辑同步消费一个 `available` 计数。`Enqueue` 保证队列内最多只有一个普通帧，因此在实际进入清理分支时，最新关键帧之后至多只有队尾普通帧，停止后恰好保留契约要求的至多两项。两项以内的队列继续由原有早退分支完整保留。

## 验收边界

本项只证明陈旧帧清理不再删除应保留的最新关键帧，并且队列项与信号量计数一致。它不宣称识别性能达标，也不证明所有页面边界和终局已经完成真实游戏 E2E 验收。
